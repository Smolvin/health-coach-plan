## [0.21.2] — 2026-09-05
### Added
- `docker/prod/docker-compose.yml` — прод-деплой: `bot` (long polling, без входящего трафика) и `admin` (веб-админка). Код и `node_modules` монтируются с хоста в общий образ рантайма (`node:20-alpine`), без своего `Dockerfile` и без пересборки образа на каждое обновление — `git pull` + `restart` применяет новый код сразу. `.env` больше не хранит инфраструктурные креды (shared MySQL/MinIO) вручную — генерируются и подставляются провижининг-инструментом инфраструктурной стороны, здесь только доменно-специфичные поля (`BOT_TOKEN`, `ADMIN_WEB_*` и т.д.). См. `docs/vps-deploy.md`.
### Changed
- **Миграции схемы БД сведены к одному базовому файлу.** Базовые таблицы (`clients` и другие, 18 всего) никогда не были зафиксированы ни одной SQL-миграцией — созданы вручную ещё до появления системы миграций (см. заметку выше про версии 0.1.0–0.4.0). На первом прод-деплое это всплыло: `npm run migrate` на свежей БД падал на первой же миграции (`ALTER TABLE clients ...` — таблицы не существует). Все 14 существовавших `.sql`-миграций удалены, текущая схема (структура без данных) зафиксирована как `migrations/00000000000000-initial-schema.sql` — сортируется первой по имени файла, `npm run migrate` дальше создаёт всю схему сам на любой свежей БД. Если у вас есть локальная среда, уже прошедшая старые миграции — ничего специально делать не нужно: её собственная таблица `migrations` просто будет содержать записи об удалённых файлах, `scripts/migrate.js` их не запрашивает повторно, работает как раньше.
### Fixed
- Первая версия прод-стека использовала кастомный `Dockerfile`, который не копировал `migrations/` в образ (`scripts/migrate.js` читает эту папку относительно `__dirname`, раньше миграции всегда гоняли с хоста напрямую — `npm run migrate`, не в контейнере, — пробел не всплывал). Переход на монтирование кода с хоста (см. выше) снял проблему полностью — `migrations/`, как и весь остальной код, читается напрямую с хоста, копировать в образ больше нечего.

### Note

Не исправлялось в этой сессии, см. `tasks.md`.

Реального клика в браузере не было — только `curl`.

- `/strategies` и список вопросов внутри `/strategies/:code` пагинацию не получили — они короткие/курируемые (стратегий буквально пара штук), а порядок вопросов внутри стратегии двигается кнопками вверх/вниз по всему массиву сразу, постраничное разбиение сломало бы эту логику. `/menu` (уровни команд бота) по той же причине — короткий курируемый список.
- lightGallery на `/gyms/:id` теперь листает только оборудование текущей страницы, не всего зала — при 24+ позициях переход на страницу 2 нужен и для просмотра галереи, не только для таблицы.
- Проверено на реальных данных: клиент с 3 раундами (41 ответ суммарно, было видно на скриншоте от пользователя) — плоская таблица исчезла, ссылки на раунды и сама страница раунда отдают верные данные и счётчики; зал с 36 позициями оборудования (размер страницы 24) — верно показывает «стр. 1 из 2», на первой странице ровно 24 карточки; несуществующий раунд — 404; счётчики клиентов (активные/в корзине) на `/clients` сверены с БД напрямую.

## [0.18.1] — 2026-08-30 03:23 IST
### Added
- Админ может отдельно выключить клиенту замеры (`/addmeasurement`/`/measurements` в боте) и/или напоминания о них — два независимых флага (`clients.measurements_enabled`, `measurement_reminders_enabled`) на карточке клиента в веб-админке. ### Note
- Выключенные замеры — «мягкая» блокировка: команды всё ещё есть в меню бота, но при нажатии отвечают, что замеры отключены, и предлагают обратиться к тренеру. Убирать команды из персонального меню конкретного клиента не стали — это отдельная (более сложная, per-chat) механика, которой сейчас ни для кого, кроме админов/владельца, не пользуемся.
- Проверено: оба флага переключаются независимо через веб-форму, `listClientsDueForReminder` корректно учитывает `measurement_reminders_enabled` (просроченный клиент с выключенными напоминаниями не попадает в список, с включёнными — попадает, независимо от флага замеров).

## [0.18.0] — 2026-08-30 02:48 IST
### Added

Новая таблица `client_surveys` — история раундов (тип: обычная/расширение, стратегия, статус, когда начат/завершён); `round` в `questionnaire_answers` теперь имеет собственные метаданные, а не просто число. `/continue` и пассивный подхват «незаконченной» анкеты научились резюмировать любой незавершённый раунд, не только первый.
- Замеры клиента (`measurement_types` — гибкий справочник параметров: вес/талия/грудь/бёдра/рука/% жира; `client_measurements` — сами записи). `/addmeasurement` в боте — клиент сам выбирает параметр и вносит значение, можно несколько за раз. `/measurements` — посмотреть свою историю.
- Бот раз в 2 недели напоминает клиенту сделать новые замеры — простой ежедневный `setInterval` внутри процесса бота (без node-cron), отбор «кому пора» на стороне SQL: последний замер (или момент создания анкеты, если замеров не было вовсе) 14+ дней назад, и напоминание не отправлялось последние 14 дней (не спамить, пока клиент тянет).
- Веб-админка: на карточке клиента — история раундов анкеты и замеров; новая функция «Добавить анкету от другого клиента (новым раундом)» — копирует конкретный завершённый раунд анкеты любого клиента как новый раунд получателю, не трогая его существующие раунды (в отличие от уже существовавшего «Скопировать данные» — тот перезаписывает всё целиком, со снимком для отката).
### Note
- `round` 2 остаётся зарезервирован под `/extend` (расширение короткой анкеты до полной) даже если клиент им ни разу не пользовался — `/newsurvey` и копирование раунда от другого клиента всегда начинают нумерацию с 3, чтобы не столкнуться номерами.
- Проверено на уровне БД и `curl`: полный цикл раунд 1 (short) → раунд 3 (`/newsurvey`, long) → раунды видно в истории; замеры + вся логика напоминаний (недавний замер — не в списке, просроченный — в списке, после отправки — не дублируется); копирование раунда между клиентами (дважды подряд — раунды 3 и 4, старое не тронуто). Реального Telegram-взаимодействия не было.

- Правка меню в `/menu` не создаёт и не удаляет сами обработчики команд в коде бота — только то, что показывается в кнопке меню; несуществующая команда в меню при нажатии ничего не сделает.

- Проверено целиком: смена состава/порядка меню + live-применение (сверено через `getMyCommands`, регрессии в исходном наборе команд нет), копирование данных клиента + откат (ответы возвращаются в точности), удаление клиента и зала (включая реальную зачистку MinIO).
