Этот файл — **публичный**, репозиторий открытый: сюда попадают только решения об архитектуре и процессе проекта. Решения, касающиеся конкретного клиента (его цели, программа, план питания), фиксируются в `clients/<slug-клиента>/decisions-log.md` — эта папка в `.gitignore` и наружу не публикуется.

## 2026-08-29 11:52 IST — версия 0.10.0

- **Решение:** «продолжить анкету» реализовано через БД, а не через сессию в памяти — при возврате клиента (в т.ч. на следующий день, когда Telegraf-сессия из памяти уже не сохранилась, например после перезапуска бота) состояние восстанавливается из `questionnaire_answers`/`clients`, а не полагается на `ctx.scene.state`, который переживает только текущий процесс.
- **Решение:** любое сообщение клиента вне активного диалога (не только `/start`/`/continue`) подхватывает недозаполненную анкету — иначе бот на такое сообщение никак не реагировал (глобального обработчика текста не было вовсе).
- **Решение:** «расширение» короткой анкеты до полной сохраняется отдельным раундом (`round = 2`) в `questionnaire_answers`, а не перезаписывает раунд 1 — чтобы не потерять уже данные ответы и не переиспользовать те же `question_number` для разных по смыслу вопросов.
- **Решение:** правки ответов админом идут через ту же функцию сохранения, что и сам сценарий анкеты (`saveAnswer` в `src/clients.js`, теперь общая), плюс отдельная запись в `answer_edit_log` — старое/новое значение, кто и когда поменял.
- **Решение:** группы клиентов — `group_id = NULL` у админа означает «видит всех», а не отдельный флаг «доступ ко всем группам» — так владельцу не нужно поддерживать список «все группы» при добавлении новой группы, снятие ограничения = один `UPDATE`.
- **Решение:** назначать клиента в группу может любой админ (организационная задача, не вопрос доступа), а вот кто из админов какую группу видит — только владелец (`/setadmingroup`), это и есть контроль доступа.
- **Обоснование:** явный запрос — можно пройти расширенную анкету после короткой, продолжить недопройденную (в т.ч. на следующий день через меню), админы могут править ответы клиентов с логированием, группы клиентов с ограничением видимости админов по группе, владелец видит все логи.
- **Статус:** все новые функции проверены на уровне данных/логики (создание клиента, полное прохождение короткой + расширение до полной, правка ответа с записью в лог, фильтрация по группе) — не проверено вживую через реальный Telegram-чат. Веб-админка группы и логи пока не показывает.

## 2026-08-29 12:23 IST — версия 0.12.0

- **Решение:** три сущности вместо двух — `gyms` (зал), `equipment_classes` (класс/таксономия оборудования, справочник) и `gym_equipment` (конкретная единица в конкретном зале с фото) — явный запрос: одно и то же оборудование должно быть представимо в разных залах, значит класс должен быть отдельной переиспользуемой сущностью, а не полем прямо на фото.
- **Решение:** фото не скачиваются и не хранятся в своей инфраструктуре — только `photo_file_id`, который Telegram и так хранит бессрочно у себя; лишний файловый стораж (S3/MinIO — на машине уже есть контейнер MinIO от другого проекта, но трогать чужую инфраструктуру не стали) не заводили.
- **Решение:** веб-админка не встраивает прямую ссылку Telegram (`getFileLink`) в `<img src>` — та ссылка содержит токен бота открытым текстом в URL, что утекло бы любому, кто откроет исходный код страницы. Вместо этого сервер сам скачивает байты и отдаёт их через свой урл (`/gyms/:gymId/equipment/:id/photo`) — токен наружу не уходит.
- **Решение:** «обработка фото» на этом этапе — это ручная классификация человеком (загрузившим фото или админом), а не автоматическое распознавание оборудования на изображении; про автоматизацию явного запроса не было, а подключать vision-модель без обсуждения — необоснованное расширение задачи. Схема данных это не блокирует — при появлении автоклассификатора он просто заполнял бы то же поле `equipment_class_id`.
- **Обоснование:** явный запрос — отдельная сущность «залы», которые заводит клиент или админ (привязка к локации или типовые), с фото оборудования, из которого формируется база оборудования зала (ещё одна сущность), плюс класс оборудования как отдельное понятие, потому что одно и то же оборудование бывает в разных залах.
- **Статус:** проверено на уровне данных и через `curl`, включая деградацию фото-прокси при недействительном `file_id` (502, не падение процесса). Реальная загрузка фото через настоящий Telegram-чат не проверялась — нужно тестировать вживую.

## 2026-08-29 12:40 IST — версия 0.13.0

- **Решение:** используем уже существующий на машине MinIO (проект `vps_local`, сеть `local_shared`) вместо своего — явный запрос пользователя; в прошлой версии (0.12.0) решили этого не делать без явного запроса, теперь запрос есть.
- **Решение:** контейнеры этого проекта подключаются к внешней докер-сети `local_shared` (`docker-compose.yml`, `networks: local_shared: external: true`) — это единственный способ дотянуться до MinIO: у него нет порта, опубликованного на хост, только сетевой доступ внутри докера. `scripts/migrate.js` по-прежнему работает с хоста (у MySQL есть host-порт), а `setup_minio.js` — только изнутри контейнера.
- **Решение:** "папка на зал" в MinIO — это префикс ключа (`gym/<id>/`) с пустым `.keep`-объектом для видимости в консоли MinIO, а не настоящая директория (у S3-совместимых хранилищ директорий не существует в принципе).
- **Решение:** отдельная таблица `gym_media` вместо замены `gym_equipment.photo_file_id` на новый столбец — так `gym_equipment` остаётся привязан к Telegram (откуда физически приходит фото), а `gym_media` — к MinIO (где оно физически хранится постоянно); одно от другого не зависит, MinIO-копия может не удаться, а Telegram-версия при этом всё равно работает.
- **Решение:** копирование в MinIO — best-effort с логированием ошибки, не блокирует сохранение фото через Telegram, если MinIO в моменте недоступен.
- **Обоснование:** явный запрос — bucket `health-coach-plan`, папка `gym`, своя папка на каждый зал, таблица маппинга медиа на MinIO, всё через отдельные скрипты `setup_minio`.
- **Статус:** полный цикл (зал → оборудование → загрузка в MinIO → чтение обратно → отдача через веб-прокси) проверен с сэмулированными байтами напрямую через `src/media.js`, без настоящего Telegram-фото — байты совпали побитово. Нужно проверить с реальной загрузкой через бота.
